# DEVICE-SUPPORT — 기기 / OS 지원 매트릭스

최근 4년 기기·OS를 어디까지 지원할지, 버전별로 무엇을 챙겨야 하는지 정리.
**앱 개발이 처음**이라는 전제로, 각 항목마다 "왜 챙겨야 하는지(💡)"를 붙였다.
숫자(점유율 등)는 출처·시점에 따라 다르니 *경향*으로 읽고, 결론(설정/테스트)을 가져갈 것.

> 우리 사용자 주 시장은 **한국**이다. 그래서 테스트 매트릭스는 **삼성 갤럭시 + 아이폰**을
> 중심으로 잡고, 글로벌 Top5는 참고로 둔다.

---

## 0. 결론부터 (이 값만 박아도 됨)

| 설정 | 값 | 이유 |
|---|---|---|
| iOS 배포 타깃 | **iOS 15** | 살아있는 거의 모든 아이폰 커버 |
| iOS 빌드 SDK | **Xcode 26 / iOS 26** | 스토어 제출 필수(2026-04-28~) |
| Android minSdk | **23** (Android 6) | 긴 꼬리까지 싸게 커버. Capacitor 8 기본 |
| Android targetSdk | **35**(곧 **36**) | 스토어 필수. 36은 2026-08-31~ |
| 화면전환 고급기능 | **iOS 18+ / Chrome 126+에서만** | 그 미만은 자동 폴백(피처 디텍션) |

💡 **왜 "최소 버전"이 중요한가**: 최소 버전을 높게 잡으면 *설치 가능한 사용자*가 줄고,
너무 낮게 잡으면 *옛 엔진 버그*를 떠안는다. 웹뷰 앱은 minSdk를 낮춰도 비용이 적어(아래 참고)
넓게 잡고, 신기능은 "있으면 쓰고 없으면 폴백"으로 간다.

## 1. iPhone — 최근 4년 + OS 지원

### 대상 기기 (출시연도)
| 연도 | 모델 |
|---|---|
| 2022 | iPhone 14 / 14 Plus / 14 Pro / 14 Pro Max, iPhone SE(3세대) |
| 2023 | iPhone 15 / 15 Plus / 15 Pro / 15 Pro Max |
| 2024 | iPhone 16 / 16 Plus / 16 Pro / 16 Pro Max |
| 2025 | iPhone 16e, iPhone 17 / 17 Pro / 17 Pro Max, iPhone Air |

### OS 지원 상황
- **현재 최신 = iOS 26** (2025-09 출시, "Liquid Glass" 디자인, 연도 기반 통합 버전명으로 18→26 점프).
- iOS 26은 **iPhone 11 이상(A13+)** 지원. 즉 **최근 4년 아이폰은 전부 iOS 26 가능.**
- iOS 26에서 제외된 건 iPhone XS/XR(A12) — 이들은 iOS 18 보안 업데이트만.

💡 **왜 iOS는 신경 덜 써도 되나**: 애플은 한 기종을 5~6년 업데이트해서 *버전 파편화가 작다*.
4년 내 아이폰이면 거의 다 최신 iOS라, iOS 18~26만 잘 보면 된다. (안드로이드와 정반대)

### iOS 버전별 체크사항
| 버전 | 체크 | 💡 왜 |
|---|---|---|
| **iOS 26**(현재) | 상태바/세이프에어리어가 반투명 디자인 위에서 잘 보이는지. App Store Connect **연령등급 설문**(2026-01~) 응답. Xcode 26로 빌드 | 안 맞추면 제출 불가/UI 가독성 문제 |
| **iOS 18 / 18.2** | View Transitions API 사용 가능(같은문서 18.0, 페이지간 18.2) | 화면전환을 네이티브급으로 — **여기부터** 켜짐 |
| **iOS 16~17** | 구형 WebKit → 일부 최신 CSS/JS·전환효과 미지원 | 반드시 **폴백** 두기(피처 디텍션) |
| **공통(웹뷰)** | `<video>`는 `muted playsinline`, 입력 폰트 ≥16px(자동 줌 방지), `100vh` 대신 `100dvh`, Universal Links용 associated domains 설정 | 초보가 가장 자주 밟는 지뢰들 |

## 2. Android — 최근 4년 + OS 지원

### OS 버전 (최근 4년)
| 출시 | 버전 | API | 비고 |
|---|---|---|---|
| 2022 | Android 13 | 33 | **런타임 알림 권한** 도입 (푸시 핵심) |
| 2023 | Android 14 | 34 | |
| 2024 | Android 15 | 35 | **edge-to-edge 강제 시작** |
| 2025 | Android 16 | 36 | edge-to-edge 강제 + 16KB 페이지 |

### 점유율 경향 (2026 초, *경향*으로만)
- 가장 큰 덩어리는 **Android 13/14/15** (각 대략 14~20%대), **16**이 빠르게 상승 중.
- 그 아래 **11/12**도 꼬리로 꽤 남아있음(파편화가 심한 게 안드로이드 특징).
- 데이터셋(Google 공식 vs AppBrain 등)에 따라 16의 비중이 7%~20%로 크게 갈림 → *숫자 맹신 금지*.

💡 **왜 안드로이드는 빡세게 챙겨야 하나**: 제조사마다 업데이트가 제각각이라 **한 버전이 몇 년씩
공존**한다. iOS처럼 "최신만 보면 됨"이 안 통한다. 그래서 버전별 동작 차이를 꼭 확인해야 한다.

### Android 버전별 체크사항 (가장 중요)
| 버전 | 반드시 체크 | 💡 왜 |
|---|---|---|
| **13 (API 33)** | **`POST_NOTIFICATIONS` 런타임 권한 요청** | 안 하면 **푸시가 조용히 안 뜸** — "푸시 고장났다"의 1순위 원인 |
| **15 (API 35)** | **edge-to-edge**: 콘텐츠가 상태바/내비바 *아래까지* 그려짐 → WindowInsets/세이프에어리어 처리 | 안 하면 헤더/푸터가 시스템 바에 가려짐 |
| **16 (API 36)** | edge-to-edge **강제(옵트아웃 불가)** + 네이티브 라이브러리 **16KB 페이지** 대응 + Predictive Back | targetSdk 36(2026-08-31~) 필수라 피할 수 없음 |
| **12 (API 31)** | 시스템 **Splash Screen API**(우리 스플래시와 겹치지 않게), PendingIntent mutability 플래그 | 스플래시 이중 노출/크래시 방지 |
| **공통(웹뷰)** | System WebView는 Play로 업데이트되지만 **Play 서비스 없는 기기(일부 화웨이/중국롬)는 구형 WebView**. 하드웨어 백버튼 처리. 카메라/파일 권한 | 백버튼 안 잡으면 앱이 그냥 종료됨 |

💡 **edge-to-edge가 뭔데**: 최신 안드로이드는 앱 화면을 상태바·내비게이션바 *뒤까지* 꽉 채운다.
대비책 없으면 우리 UI 상·하단이 시스템 바에 먹힌다. Capacitor가 상당 부분 처리하지만 **실기기로
반드시 확인**해야 한다.

## 4. 푸시 신뢰도 — 제조사 주의 (초보 함정)
- 샤오미·오포·비보·(일부 삼성 설정)는 **백그라운드 앱을 공격적으로 죽여** 푸시가 안 올 수 있음.
- 대응: 배터리 최적화 예외 안내, 중요한 알림은 서버 재시도, FCM high-priority 적절히 사용.

  보면 "잘 된다"고 착각한다.

## 4b. 디스플레이 다양성 대응 레시피 (해상도/종횡비/컷아웃/폴더블)

거의 다 **웹 CSS**로 푼다. 앱은 edge-to-edge(iOS `contentInset:never`)로 노치/홈인디케이터까지 콘텐츠가
확장되므로, 상/하단 고정요소(헤더·탭바·버튼·컴포저)는 **반드시 세이프에어리어 인셋을 적용**해야 한다.
하네스는 이를 **이중으로 보장**한다:
① `@capacitor-community/safe-area` 가 `--safe-area-inset-*` CSS 변수 주입(뷰포트와 무관하게 항상 동작),
② 브릿지 `ready()` 가 원격 페이지 viewport meta 에 `viewport-fit=cover` 를 **자동 주입**(웹이 빠뜨려도 `env()` 동작).
→ 그래서 아래 `var(..., env(...))` 패턴이 어떤 앱에서든 동작한다. **bare `env()` 단독 사용은 피하고 이 패턴을 써라.**

```css
/* 노치/펀치홀/제스처바: 플러그인이 주입한 변수 사용(Android env() 불안정 보완).
   ★ 인셋을 그대로 주는 건 **자기 여백이 없는 요소**일 때만이다.
     헤더·탭바처럼 이미 padding 을 가진 바는 바로 아래 항목을 따라라. */
.screen-top { padding-top: var(--safe-area-inset-top, env(safe-area-inset-top, 0px)); }
.footer { padding-bottom: var(--safe-area-inset-bottom, env(safe-area-inset-bottom, 0px)); }

/* 100vh 금지 → dvh (주소창/키보드로 높이 변함) */
.screen { min-height: 100dvh; }

/* 해상도/DPI: 고정 px 대신 반응형 단위 + 이미지 srcset/WebP */
```

- **이미 여백이 있는 바에 인셋을 통째로 더하지 마라 — 가장 흔한 실수다.** 헤더·탭바는 거의 항상
  자기 상하 패딩을 갖는다. 거기에 인셋을 그대로 더하면 두 여백이 쌓여 바가 부푼다. 노치를 피하는 데
  실제로 더 필요한 양은 **`인셋 − 그 바가 이미 가진 여백`** 뿐이다.
  ```css
  /* 바깥 바가 노치 보정을, 안쪽 내용 행이 원래 여백을 갖는 구조 */
  :root {
    --bar-pad-y: 12px;  /* 내용 행이 이미 가진 상하 여백 */
    --bar-h: 64px;      /* 인셋 0(웹) 기준 바 높이 */
    /* 부족한 만큼만 민다. 인셋 0 인 웹에서는 0 → 웹 레이아웃은 변하지 않는다. */
    --bar-safe-pad: max(0px, calc(var(--safe-area-inset-top, env(safe-area-inset-top, 0px)) - var(--bar-pad-y)));
    /* 바가 화면 상단에서 실제로 차지하는 총 높이 */
    --bar-inset: calc(var(--bar-safe-pad) + var(--bar-h));
  }
  .bar      { padding-top: var(--bar-safe-pad); }
  .bar__row { padding-block: var(--bar-pad-y); }
  ```
  **왜 이렇게까지 하냐**: 팝챗이 인셋을 통째로 더했다가 다이내믹 아일랜드 기기에서 헤더가 126pt 까지
  부풀었다(인셋 62 + 헤더 64). 섬은 51pt 에서 끝나므로 로고까지 **34pt 가 빈 띠**로 남았고, 같은 기기의
  iOS 네이티브 내비게이션 바는 106pt 였다. 위 방식으로 114pt 가 됐다(시뮬레이터 실측 2026-09,
  17 Pro·17·Air·16e·iPad mini 전 기기에서 정확히 `pad-y` 만큼 축소, 웹은 변화 0).
- **바 아래에 무언가를 앉힐 땐 `env() + 숫자` 를 새로 쓰지 말고 위 `--bar-inset` 같은 총합 값을 써라.**
  스페이서·플로팅 버튼·시트가 각자 `env() + 64px` 를 하드코딩하면, 바 높이나 노치 보정 규칙을 바꿀 때
  그 값들만 홀로 어긋난다. 화면 가장자리에 붙는 플로팅 컨트롤처럼 **바와 무관한** 것만 인셋을 직접 쓴다.
- **상단 중앙 카메라 컷아웃**: `safe-area-inset-top` 이 콘텐츠를 그 아래로 밀어줌 → 최상단 중앙(상태바 존)에
  탭 타깃 두지 말 것.
- **폴더블(갤럭시 Z)**: `window.addEventListener('resize')` / `matchMedia` 로 펼침·접힘 레이아웃 전환. 고정 종횡비 가정 금지.
- **JS 로 인셋이 필요하면**: `AppBridge.getSafeAreaInsets()` (또는 어댑터 `safeAreaInsets()`).
- **키보드(iOS)**: 앱은 edge-to-edge(`contentInset:never`)라 콘텐츠가 화면 하단까지 닿는다. 입력창을 키보드
  위로 올릴 때 **iOS도 Android/웹과 동일하게 키보드 높이만큼만** 리프트하라. 과거 `contentInset:'always'`
  시절의 `- env(safe-area-inset-bottom)` 보정을 넣으면 그만큼(≈34px) 입력줄이 키보드에 가려진다.
- 실기기 확인: 노치 아이폰 + 펀치홀 갤럭시 + 폴더블 1대(§3 매트릭스).

## 5. 한 줄 운영 가이드
- iOS: 4년 내 기기 = 거의 다 iOS 26 → **iOS 18~26만 잘 보면 됨**, 18 미만은 폴백.
- Android: **13(알림권한) · 15/16(edge-to-edge)** 이 2개만 놓쳐도 "푸시 안 옴 / UI 잘림"이 바로 터짐.
- 테스트: **갤럭시 중급기 1대 + 폴더블 1대 + 구형 아이폰 1대**는 꼭 실기기로.
